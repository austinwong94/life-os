## October 16: Cross-Tab Session Renewal (Local Candidate)

**Reproduced:** the original four-caller/two-tab renewal test failed on baseline repeat 19, making two requests instead of one. Its retained synthetic trace showed both expired fixture writes occurring before renewal, the first tab publishing and reading back the rotated session, then the second tab briefly reading the old session inside the existing shared auth lock. That tab read the newer session just afterward, but its old-token request had already started. This was not dismissed as a fixture reseeding issue or fixed by increasing a sleep. The observation establishes stale-read behaviour in the test, not a particular browser-engine defect.

**Related safety defects also reproduced before correction:** the valid-cache fast path returned credentials despite an observable sign-out, a different stored owner, malformed storage, or disagreement with the recorded data owner when the other tab's storage notification was withheld. Four rejection tests failed before the correction. A separate forced-stale-storage case reproduced another exchange of an already-renewed token and an unsuccessful credential readback.

### Implemented

- **Hash-only rotation receipts:** `auth-renewal.js` adds an origin-private, scope-named IndexedDB registry under the existing `life-os-auth-refresh-v1` Web Lock. Each key is the SHA-256 digest of one refresh token. Values contain only a format, pending/applied status and random attempt ID: no token, password, email, user ID, diary, note or task is copied into it. Existing credentials remain in their original session key; this is not new encryption or an authoritative login store.
- **Claim before exchange; acknowledge after publication:** a strict-durability pending claim and readback are required before making the auth request. A receipt becomes applied only after the rotated same-owner credentials are saved and read back successfully. A tab still observing an already-applied token refuses to exchange it again; it adopts a newly visible valid same-owner session or reports a retryable wait while retaining credentials and writing. No arbitrary readiness delay, changed server reuse interval or disabled security setting was introduced.
- **No false proof from an uncertain attempt:** pending does not claim the server rotated a token. Temporary outages, lost responses and failed credential publication leave the pending state and original credential bytes available for recovery. The synthetic lost-response test issues one server token pair, loses its response, and returns that existing active pair on retry. This follows the documented [Supabase parent-token recovery exceptions](https://supabase.com/docs/guides/auth/sessions), not a change to server token-reuse protection. The [current changelog](https://supabase.com/changelog) was also reviewed; no provider settings, SDK or backend API migration was needed here.
- **Earlier owner and sign-out checks:** both cached and renewing paths now require a well-shaped currently stored identity, matching session owner and recorded data owner. Ownership is checked again after asynchronous receipt/network work. Observable sign-out, another owner's credentials and malformed original bytes are refused without deleting or replacing that stored session, making a cloud request, or changing any board. Malformed provider credentials are also refused before publication, retaining the original session and pending receipt. Authorization still depends on the real provider and database policies, not user metadata or a client hash receipt.
- **Finite failure handling:** denied, full, blocked, malformed or stalled receipt storage stops verification without discarding the session or records. Open/transaction work has a ten-second deadline. Tests verify release of the auth lock and retry after storage recovery. A failed final receipt does not erase already-published credentials or report verified renewal. Existing account password setup, restore pauses, cloud retry budgets and canonical record/merge formats remain unchanged.
- **Packaging and CI:** the new module is allowlisted and covered by the required-module guard; incomplete older HTML cannot open records with a partially updated dependency set. The isolated session suite runs in both browser engines in CI. Optional renewal traces contain only synthetic credential labels, timing and stacks, not real credentials or private records. Test outputs remain outside the public artifact.

## October 16: Interrupted Cloud Saves And Reconnect Recovery (Local Preview Only)

**Gaps addressed:** an online browser encountering a temporary cloud failure could wait for another edit/focus change before trying again. ### Implemented

- **Bounded automatic retry:** transient transport failures, selected temporary HTTP failures and conditional-write collisions can retry after 5, 15 and 45 seconds. There is one pending retry timer per tab, with three retries per cycle. A representable server Retry-After wait is not shortened. Exhaustion is explicit; Save cloud starts a fresh attempt. Offline events cancel pending network timers, and reconnect starts a fresh comparison using the existing sign-in. New writing added while waiting remains in the original device records and is included in the next eligible save.
- **Eligibility is rechecked:** retries stop when the owner changes, sign-in requires attention, saving is disabled, device saving has failed, restore protection is active or genuine comparisons need review. Permission/validation failures are not blindly retried. Switching accounts or signing out clears the queued retry and uncertain-upload proof. This is not permission to change accounts, resolve old comparisons or overwrite older cloud copies.
- **Finite request deadlines:** cloud row reads, including body reading, have a 15-second deadline; uploads have 60 seconds to accommodate larger payloads. An abort does not prove the server rejected a write. Subsequent attempts therefore read the current row and reuse the existing owner checks, merge and conditional-write protocol; they do not blindly resend a cached payload. A known HTTP permission failure stays non-retryable even if its error body stalls.
- **Exact acknowledgement, not a latest-clock guess:** this tab retains its attempted upload in memory. Only a fresh row matching its owner, complete payload and generated revision can establish that intermediate copy as a verified sync baseline. Later local writing remains untouched and is merged from that baseline. A changed server revision, different payload or changed restore guard cannot use that proof. Successful readback clears it. Reviewed restore cancels the retry and clears the proof without removing any diary/task records.
- **Validation and honest status:** an unexpected successful response is rejected rather than mistaken for an empty cloud and followed by an insert. Waiting retries are labelled as device-saved, cloud-unconfirmed. Exhausted attempts retain device records and explain the retry action. Temporary sign-in renewal failures can resume the pending save through the existing same-owner renewal flow without creating an account or discarding credentials.

The small `cloud-transport.js` boundary separates request deadlines/status classification and timer policy from record merging; it has no credentials or record store of its own. Current [Supabase sessions guidance](https://supabase.com/docs/guides/auth/sessions) and [PostgREST error documentation](https://docs.postgrest.org/en/stable/references/errors.html) were checked alongside the [Supabase changelog](https://supabase.com/changelog).
